4Operating modes and failover

Each GitLab target is always in one of three modes. The engine stores the mode, and it changes only through the commands shown.

4.1 What promote does

  1. Records the promotion before changing anything, and updates the record after every step. A crash part-way can always be undone.
  2. Stops the GitHub source, so the engine writes nothing more from GitHub.
  3. Restores real branch protection, replacing the bot-only rule with the rules archived from GitHub (required reviews, who may push, force-push).
  4. Enables CI/CD on every project (it is off while mirroring).
  5. Turns mirror accounts into real ones. Humans are unblocked and get their company email. Bots and former members stay blocked. The temporary Owner role is removed, and real roles are applied: org admins become Owners, members get the base permission, teams become subgroups with project shares, and collaborators become project members.
  6. Posts a banner on every page ("GitHub is unavailable: this GitLab is now our primary code host…").
  7. Feeds the other GitLab with push mirrors from every project on the primary. The engine allows the secondary's host through GitLab's outbound-request protection when it is on a private network.
  8. Prints the RPO: for every repository, the time of the last successful sync from GitHub.

A step that fails for one item (one project, one account, one mirror) is listed under failures and alerted, and the rest of the failover continues. The command then exits with code 1. demote reverses exactly what the record lists. It exists for drills and for returning to GitHub if it comes back.

4.2 After failover

Two things to know 1. GitLab runs a push mirror that covers all branches at most once every 5 minutes, so the secondary trails the primary by up to 5 minutes.
2. After failover only git data flows to the secondary. Issues and MRs created on the new primary reach the secondary only through GitLab's project export/import. A GitLab-to-GitLab metadata adapter is not built yet (section 9).

4.3 Recovery objectives

ObjectiveValue
RPO (data loss)Normally seconds: webhooks trigger syncs immediately. The worst case is the scheduler interval for a missed webhook (metadata 1 h, git 6 h by default). promote prints the exact value per repository.
RTO (time to work again)promote takes minutes. The rest is communication: the banner, the remote URL change (a one-line git command or an MDM-pushed insteadOf rule), and SSO login.

5.2 Step 1 — GitLab on each side

If a GitLab is already running, skip this step. Otherwise deploy/gitlab/docker-compose.yml is a ready template, pinned to the tested version 19.5.3. Set external_url and put the root password in root_password.txt:

cd deploy/gitlab && echo 'a-long-root-password' > root_password.txt
docker compose up -d                 # first boot takes 5–10 minutes
  • Git over SSH is published on port 2222, so the host's own SSH keeps port 22. The engine's side channel uses the host's SSH.
  • Uncomment the three SSO lines (omniauth_allow_single_sign_on, omniauth_auto_link_user, omniauth_block_auto_created_users = false) once your identity provider is configured. Failover then needs no account work.

5.4 Step 3 — Prepare each GitLab host

When setup reaches “GitLab targets”, open a second terminal on the engine host and run the printed line once per GitLab host, replacing <admin>@<gitlab-host>. The script travels over your own SSH session, so nothing needs to be installed first. Then paste the last line it prints into setup.

The script is idempotent, so running it again is harmless and issues a fresh token. It does four things:

  1. Side-channel login. It creates a Unix user ghmirror that can log in only with the engine's key, without port forwarding or a terminal.
  2. Exact sudo rule. /etc/sudoers.d/ghmirror allows gitlab-rails, sh and pkill without a password and nothing else. Every path sudo might resolve is listed. For a Docker-hosted GitLab the rule is docker exec -i <container> * instead, and the container is found automatically.
  3. Mirror bot. It creates the GitLab administrator github-mirror and a token with the scopes api, sudo, admin_mode, read_api, write_repository.
  4. One line for setup. It prints the URL, token, SSH login and the host's SSH key. The engine therefore trusts exactly this host, and nobody has to confirm a fingerprint. The line stays under 1024 characters, the most a terminal accepts in one paste.
OptionUse when
--container NAMEMore than one GitLab container runs on the host.
--ssh-host HOSTThe engine reaches the host under another name or IP than hostname -f.
--ssh-port PORTThe host's own sshd is not on port 22.
--bot NAME, --token-days NAnother bot username, or a token lifetime other than 365 days. Rotate by re-running the script and setup before it expires.
Security notegitlab-rails runner can run any code with GitLab's privileges, and sudo sh is a root shell. The side channel is therefore as powerful as root on the GitLab host. Treat the engine host and secrets/id_ed25519 like GitLab's root account: a dedicated host, restricted logins, and the key used for nothing else. If that is not acceptable, remove side_channel from ghmirror.yaml. The engine still works, and only the fields in §3.5 lose their original values.

5.5 Step 4 — GitHub access and webhooks

GitHub App (recommended). Setup builds the App definition for you: read-only access to contents, metadata, issues, pull requests, discussions and administration, members on the organization, and the events the engine handles. It then sends your browser to GitHub with everything filled in. Click Create GitHub App, then Install. Setup receives the App's ID, private key and webhook secret directly from GitHub, and detects the installation by itself.

  • Engine on a remote server? Run ssh -L 8765:localhost:8765 <engine-host> from your laptop first, so the browser can reach setup. If the page GitHub returns to does not load, copy its address from the browser into setup instead.
  • Token instead: answer token and paste a classic PAT (repo, read:org; add admin:org_hook and setup also creates the organization webhook). For a personal account, a token is the simplest choice.

Webhooks make changes appear within seconds. GitHub must reach https://<your-host>/webhook, so route that path to 127.0.0.1:8080 on the engine host with your reverse proxy or a tunnel. With no public URL, answer Enter: the engine then polls every 15 minutes and nothing else changes.

5.7 The first copy

Setup queues a full pass for every repository, and the service works through it: git first, then issues, pull requests and reviews, then members. It is idempotent and resumable. A restart or a crash continues where it stopped, and nothing is duplicated. Until a repository's first copy is done, the parity report lists it as pending rather than as drift, so a new install does not raise false alarms.

docker compose run --rm engine status      # queue: pending / running / done
docker compose logs -f engine              # live progress
docker compose run --rm engine verify      # "drift_count": 0 when the copy is complete

Expect about one GitHub API call per object. A GitHub App installation gets at least 5,000 calls per hour, more for large organizations and on Enterprise Cloud. For very large organizations, narrow source.repos.include first and widen it in steps.
