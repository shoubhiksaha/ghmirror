11Security architecture and threat model

The engine host holds the keys to both GitLabs and a full copy of the code, so it must be protected like the GitLab servers themselves. This chapter summarises docs/SECURITY.md. Every statement there was checked against the code.

11.1 Trust boundaries

BoundaryAuthenticationProtection
GitHub → engine (webhooks)HMAC-SHA256 over the raw body, constant-time comparison. With no secret configured, every webhook is refused (fail closed). Bodies over 26 MB are refused; duplicate deliveries are dropped.The engine listens on 127.0.0.1:8080 behind your proxy. A webhook only queues a job, and the job re-reads the object from GitHub, so webhook content is never trusted.
Engine → GitHubGitHub App installation token (1-hour lifetime) or a token.The App is read-only: contents, metadata, issues, pull requests, discussions, administration, members. It cannot write to GitHub.
Engine → GitLab APIAdmin bot token (api sudo admin_mode read_api write_repository), 365-day lifetime by default.HTTPS. One token per GitLab, so a leak does not cross to the other GitLab. check reports the days left.
Engine → GitLab host (side channel)SSH key only, with the host key pinned at setup (StrictHostKeyChecking=yes).The login has no pty and no forwarding. The agent runs a fixed set of operations.
People → GitLabGitLab's login, SSO, 2FA.While mirroring, mirror accounts are blocked and people have read access only.

Git credentials travel in http.<url>.extraheader through GIT_CONFIG_* environment variables. They never appear in a remote URL, in ps output or in .git/config.

11.2 Threats and mitigations

ThreatImpactMitigation
Engine host compromisedHighest: admin of both GitLabs, root on both GitLab hosts, read access to every repository, the full copy on disk.Dedicated VM, disk encryption, no inbound ports except /webhook, operator SSH with keys and 2FA, secrets in 0600 files, encrypted backups of .env and secrets/.
Side-channel key stolenRoot-equivalent on that GitLab host: gitlab-rails or docker exec can run any code.Key unique to ghmirror; pinned host key; from="<engine IP>" in authorized_keys or a firewall rule; audit ghmirror logins. If unacceptable, run without the side channel (§9).
Bot token leakedAdmin API on one GitLab.Limited lifetime; revoke in the admin area; audit events (EE).
Forged webhooksWithout a secret: work queued (denial of service). No data change.HMAC with a 256-bit secret, fail closed, size cap, de-duplication.
Mass deletion on GitHub (stolen admin, ransomware, mistake)Copies destroyed, if mirrored blindly.ghmirror never deletes issues, merge requests or projects. Deleted repositories are archived. The deletion guard halts all writes on a mass disappearance. Rewritten git refs keep their old tips in L1, and commits that exist only on GitLab are saved before a ref is reset (E29).
A GitLab instance compromisedThat copy read or altered.Data flows only from GitHub. The nightly verify detects changes and --repair restores them.
/status, /metrics exposedRepository names and queue state revealed.Both are bound to localhost. Expose only POST /webhook.

11.3 Hardening checklist

Before going live
  • Dedicated, encrypted VM.
  • Only POST /webhook exposed, over HTTPS.
  • A GitHub App rather than a personal token; GITHUB_MIGRATION_TOKEN empty unless needed.
  • GitLab URLs on https://.
  • from= restriction on the side-channel key.
  • Token rotation reminder; alerts to a watched channel.
  • Backups of secrets kept apart from the data.
  • A failover drill twice a year.
Known limitations:
  • The side channel is root-equivalent by design.
  • Volumes are not encrypted by ghmirror itself.
  • /status and /metrics are unauthenticated.
  • Rotation is manual.
  • There has been no external audit yet.

13.2 Exact limits of the offline (on-premises) copy

LimitDetail
Not air-gappedThe engine pushes to it over the network and must reach GitHub at the same time. There is no export-to-media mode.
Read-only while mirroringChanges made by hand are reported by verify and may be overwritten from GitHub. Commits that exist only on GitLab are saved first (E29).
FreshnessSeconds with webhooks, up to 15 minutes when polling; catches up after engine downtime.
After failoverThe secondary receives git only, within 5 minutes. Issues and merge requests created after the failover are not copied to it.
Links in textAttachments, avatars and release assets are copied; links in text still point at GitHub.
CIDisabled while mirroring, enabled by promote. Runners and variables must be prepared on the offline GitLab.
One engineOne engine feeds both GitLabs. If it is lost, updates stop, but the copies stay intact.
Restore from L2Manual (scripted). The fast path is a new first copy from GitHub, or export/import from the surviving GitLab.
