3How it works

3.1 Components

ghmirror is one Python service (the engine), packaged as a Docker image, with a PostgreSQL database for its state. It reads from GitHub over the REST and GraphQL APIs and git. It writes to each GitLab through the REST API, git pushes, and a small side channel for the few fields the API cannot set.

3.2 Three layers of copy

The design keeps three independent copies of the organization. Each layer protects against a different failure.

3.3 Mirror accounts (identity)

For every GitHub user who appears in the data, the engine creates a GitLab account with the same username, display name, avatar, SSH keys and GPG keys. Accounts are matched by a hidden marker (ghmirror github_id:<id>) in the admin note, so renames and re-installs never create duplicates.

While mirroring, nobody can log in as a mirror account and nothing can be pushed by hand. The copy stays an exact image of GitHub. At failover, promote activates the human accounts, applies their company e-mail from identities.yaml and gives each person the role they had on GitHub. This is the only change needed to "turn mirror accounts into real accounts".

3.4 Same numbers, same diffs

Numbers. GitHub numbers issues and PRs in one shared sequence (#1, #2, #3…). GitLab has separate counters for issues and merge requests. The engine creates objects strictly in number order and keeps them aligned: issue #2 stays issue #2, and PR #3 becomes merge request !3, not !1. If anything ever breaks the alignment (for example a failed create), the side channel renumbers the MR and its git ref, and later creations wait until it is fixed.

Diffs. Recreating a merged PR naively against main would show an empty diff, because main already contains the change. The engine instead pushes the PR's head and base commits to hidden refs, opens the MR between them, so GitLab stores the exact reviewed diff, then sets the real target branch, state, merger and dates. Line comments are placed on the same file, line and side as on GitHub, including multi-line ranges.

3.5 The side channel

The GitLab API lets an admin create objects as another user and backdate most of them. A few fields are read-only in the API: MR creation date, merged and closed state with merger and time, approval dates, release author, and the MR number itself. For these, the engine runs a small Ruby agent inside GitLab's own Rails environment (gitlab-rails runner), reached by the configured command prefix (typically ssh gitlab-host sudo).

  • One agent per engine process. Rails boots once, and operations then stream as JSON lines in batches.
  • Every operation is idempotent and written to the audit log.
  • Each agent has a unique token. On exit or timeout it is killed on the GitLab host (pkill -9), and it exits by itself after 15 minutes without input, so it cannot leak memory on the server.
  • Without a side channel the engine still runs. Those few fields then fall back to "now", and the parity check reports them.

3.6 The sync pipeline

  1. Event. A GitHub webhook (push, issues, pull_request, review, comment, release, member, repository…) or a scheduled pass creates a job.
  2. Queue. Jobs are stored durably. Repeated events for one repo collapse into one job, and two workers never touch the same repo at once.
  3. Git. The bare mirror is fetched (branches, tags, PR heads) and pushed ref-exactly to every target. Branch deletions use the API because the mirror's protection rule blocks deletion by push.
  4. Metadata. Labels, milestones, then every issue and PR in number order with comments, reactions, reviews and line comments, then releases and assets. Each object is matched through the id map. If the map is lost, existing GitLab objects are adopted by number, name or author, time and body instead of being created twice.
  5. Side channel. The fields from 3.5 are applied in one batch per repo.
  6. Verify. A nightly field-by-field comparison in both directions. Drift raises an alert, and --repair re-queues the affected objects.

3.7 Safety mechanisms

RiskMechanism
GitHub org deleted, suspended or hackedCircuit breaker. If the owner returns 404, or more objects vanish in one pass than allowed (default: over 2% and over 1 item), all writes stop immediately with an alert. The mirrors keep the last good state.
A repo or issue deleted on GitHubThe repo is archived on GitLab, never deleted. The issue is closed and labelled deleted-on-github.
History rewritten (force-push)The old tip is saved under refs/ghmirror-backup/<time>/… before the mirror follows.
Slow or overloaded GitLabRetries with back-off on 429/5xx. A create whose outcome is unknown (timeout, 502) is looked up before it is resent, so no duplicate issues, notes, MRs or accounts are made.
Engine crash mid-wayJobs have leases and are retried. All steps are idempotent. A crashed promote can always be undone by demote.
Silent divergenceNightly verify: refs, numbers, titles, authors, dates, states, merger, labels, note counts, milestones, releases, and objects that exist only on GitLab.
Someone edits the mirror by handMirror accounts are blocked and only the bot may push (protected * rule). Verify reports anything else.
