In steady state the mirror needs no attention. This chapter covers the few situations that need a person. Run every command from deploy/compose/ on the engine host, as docker compose run --rm engine <command>.

7.2 When the deletion guard halts

The engine stops all writes when the GitHub owner returns 404, or when more repositories or issues vanish in one pass than guard.max_disappear_* allows. A single deleted repository does not halt anything: it is archived on GitLab (Figure 19). On ghmirror_halted 1:

  1. Look at GitHub: the organization page, githubstatus.com, the App installation.
  2. GitHub is fine, for example you moved many repositories on purpose: run guard reset. Mirroring resumes and catches up.
  3. GitHub is gone or compromised: do not reset. The GitLab copies are frozen in their last good state. Go to §7.3.

7.3 Failover checklist (GitHub lost)

  1. Decide the primary. Usually cloud, which is reachable from everywhere. Use offline if the cloud is affected too.
  2. Promote: promote --primary cloud. Type promote to confirm. It prints the state, the users activated, the mirrors and the RPO (last successful sync per repository). Exit code 1 means some steps failed, and each failure is listed. Fix the cause, then run demote and promote again.
  3. Redirect old links: docker compose --profile failover up -d redirector, and point bookmarks and documentation links (or a vanity DNS name) at it. Old github.com/<org>/<repo>/pull/7 links then land on !7.
  4. Tell developers to run one command per clone, or push url.<new>.insteadOf <old> through device management: 
    git remote set-url origin git@gitlab.acme.com:acme/<repo>.git     # same SSH keys work
  5. Sign-in: with SSO, the first login links each person to their account automatically (§4). Without SSO, an administrator sends password resets from Admin › Users.
  6. CI: CI/CD is enabled on promote. Re-create secrets as GitLab CI variables; GitHub never exposes them.
The secondary trails by up to 5 minutesAfter promote, the other GitLab is updated by push mirroring, which GitLab runs at most once every 5 minutes per project. Only git data flows to it. Issues and MRs created after failover exist on the primary only.

7.4 Monthly drill

Practise on a snapshot of the offline instance or on a scratch GitLab, never on the live cloud mirror: promote → two engineers clone, branch, open an MR, approve, merge and tag → demote → delete the merge requests and issues made during the drill → sync --full → verify must report 0 drift. Steps 11–13 of e2e/run_e2e.sh automate exactly this (§8.1); chapter 14 shows a recorded drill.

The cleanup matters. Right after demote, verify reports the drill's work: branches that moved and merge requests that exist only on GitLab. ghmirror never deletes them itself. The next sync resets the branches to GitHub, and any commit that exists only on GitLab is first saved in the engine's git mirror under refs/ghmirror-backup/<time>/target/. Merge requests and issues stay until a person deletes them. A drill MR left in place (say !8) also takes the number that GitHub's next PR #8 needs. This is why drills belong on a snapshot.

7.5 Rebuilding a lost GitLab

SituationProcedure
GitHub still availableNew empty GitLab → prepare-host.sh → ./setup.sh (paste its line). The first copy rebuilds it exactly, like the original seed.
GitHub gone, the other GitLab aliveMove the group from the surviving GitLab with GitLab's own group and project export/import, or Direct Transfer. Issues, MRs, notes and history are kept.
Both GitLabs goneCode: git push --mirror from the bare mirrors in the mirrors volume. Metadata: preserved as JSON in the archive volume, plus GitHub's own migration archives if a migration_token is set. Replaying JSON into GitLab is not automated (§9).

Back up the engine host's mirrors and archive volumes with your normal backup tool. With them, the code and the full record survive even if every hosted copy is lost.

8.4 Defects found and fixed during testing

Each one is recorded in ROADBLOCKS.md with its cause and fix, and each is fixed and verified.

IDFinding
E11A create that times out after GitLab has already written could be re-sent and duplicate the object. Every create now finds and adopts the existing object first.
E12GitLab refuses push mirrors to private-network hosts, which is where an offline secondary lives. Promote adds the secondary's host to the outbound allowlist and uses its mirror_url.
E13Stopping the local ssh/docker exec did not stop the Rails agent on the GitLab host. Each agent now carries a token, is killed on the host, and exits by itself when idle.
E14Two GitLabs on one 8 GB host overload: sizing guidance (§5.1), side-channel boot wait raised to 45 minutes.
E15–E16Push mirrors run at most every 5 minutes; GitLab's branch cache lags. Both are documented and handled.
E17verify now also reports objects that exist only on GitLab.
E18–E19Promote interrupted midway: demote restores everything. An unreachable secondary at promote is now a reported failure, not a silent skip.
E20–E22Side channel over real SSH: argument quoting, pkill self-match, sudo path matching.
E23–E24Compose stack: mounts, volume ownership, secret permissions, port clash, database start-up race.
E25GitLab 19's new name-clash message; personal-account group naming.
E26–E28Paste-length limit of terminals; a false drift alert on day one; weekly migration alert noise with GitHub Apps.
E29A branch made by hand on a mirror was removed by the next ref-exact push. Commits that exist only on GitLab are now saved in the engine's git mirror (refs/ghmirror-backup/<time>/target/) before any ref is deleted or overwritten. Verified live (chapter 14).
E30Every push re-versioned every PR in the L2 archive (timestamps of the embedded repository changed). Volatile fields of embedded repositories no longer count as a change.
E31Large-history test (git/git): git notes never reached GitLab, and the engine fetched them only on its first clone. Notes are now fetched, pushed and compared like branches and tags; existing mirrors upgrade themselves. Verified live (§12.3).

9Limits and known gaps

AreaLimit
Not exercised end to endOrganization teams and members, GitHub App authentication against live GitHub, wikis and LFS are implemented and unit-tested, but the live tests used a personal account and a token.
No GitLab equivalentGitHub Discussions, Projects (boards), Actions run history and logs: not copied and not archived.
Never availableSecret values (Actions secrets, private halves of deploy keys): GitHub never exposes them. Re-create them in GitLab.
Side channel neededMR creation dates, squash-merged state and approval dates need the side channel. Without it they become notes.
Restore from L2The JSON archive is not replayed into GitLab automatically. Rebuild from GitHub or from the other GitLab (§7.5).
After failoverThe secondary receives git data only, and up to 5 minutes late. The engine no longer syncs metadata between the GitLabs.
UsernamesA mirror account takes the GitHub login. If a GitLab user or group already has that name, it becomes <login>-gh and the engine log records it. Check Admin › Users after the first copy.
HostingSelf-managed GitLab only. GitLab.com cannot impersonate users or set historical dates. Tested on 19.5.3; re-run check and verify after upgrades.
SecurityThe side channel is root-equivalent on each GitLab host (§5.4). Protect the engine host accordingly.
